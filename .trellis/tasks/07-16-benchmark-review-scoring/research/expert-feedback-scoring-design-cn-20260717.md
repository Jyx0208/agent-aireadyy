# 专家反馈驱动的 Discovery 评分系统设计记录

> 日期：2026-07-17  
> 用途：Benchmark Review 后续设计、GrillMe Q7b 规模设计及周报素材  
> 状态：设计讨论结论，尚未进入正式实现

## 1. 背景与问题

当前一键建池的 Web Discovery 默认预算为 `max_projects=5`、`max_files=50`、`max_candidate_projects=50`，导致用户要求“越多越好”时，最终评审池仍可能只有约 4～5 个项目。Pool builder 和专家 workflow 本身没有四项目上限：用 2,000 个 Discovery 项目做管理器级验证时，可以生成 2,000 个项目候选。

现有 Discovery 同时存在多套分数：

- `project_score`：基于关键词、物种、采集方式、PTM/免疫肽语义和元数据字段的项目级启发式分。
- `file_score`：基于文件类型、文件名语义、采集方式和标记方式的文件级启发式分。
- `task_ai_readiness_score`：文件对具体下游任务的就绪度，范围 0～1。
- `data_value_score`：综合任务就绪度、标签产量、多样性、新颖性、成本和风险的文件价值分，范围 0～1。
- `expert_consensus_grade`：异构专家模型对整个项目给出的 0～3 序数等级。

这些分数当前语义不统一，也没有经过专家标签校准。`project_score/file_score` 可以用于快速排序，但不应被解释为科学校准后的可用概率或最终结论。

## 2. 总体结论

采用“专家反馈驱动的序数学习/排序学习”是科学且可行的方向，但需要满足以下条件：

1. Hard gate、启发式特征、学习模型预测和专家共识必须分层保存，不能混成一个来源不明的分数。
2. 用户界面可以统一展示 0～3 分，但内部必须保留特征值、等级概率、置信度、证据和评分来源。
3. 不应在每个专家标签产生后立即在线修改权重；应批量、离线、版本化训练，验证通过后再发布。
4. 初期优先使用序数逻辑回归或带单调约束的树模型；数据量不足时不需要神经网络。
5. 专家模型标签是高质量伪标签，不等于真实人类金标准。未来人类专家标签应拥有最高校准权重。
6. 项目质量分与项目集选择价值必须分开：多样性、覆盖增益和冗余属于集合级目标，不应全部塞进单项目分。
7. 当前阶段没有真实人类专家，“专家”必须由不同底层模型家族的 Agent 承担；同一模型换 Prompt、换角色或重复调用不能被视为独立专家。

## 3. 建议的评分流水线

```text
自然语言 Prompt
→ LLM 解析任务、硬约束、目标规模和英文 query_terms
→ Repository Discovery
→ Hard gate
→ 项目/文件特征计算
→ Discovery 预测等级 0～3 + 概率 + 置信度
→ 不确定/边界/高价值项目进入异构专家评审
→ 专家共识等级 0～3
→ 累积训练样本
→ 离线更新评分模型
→ 分组验证、影子运行、版本发布或回滚
→ 项目集优化与集合总分
```

## 4. Hard gate

Hard gate 独立于软分，失败不能被高相关度、文件数量或专家平均分抵消。典型条件包括：

- 用户严格限定物种，但项目明确属于其他物种。
- 用户严格限定 DDA，但项目明确只有 DIA/PRM/SRM/MRM。
- 用户要求免疫肽/HLA ligandome，但项目明确没有相应实验或文件子集。
- 没有任何可下载且受支持的目标文件。
- 用户要求的必要文件角色完全缺失。

Hard gate 输出应为：

```text
pass / fail / unknown
```

`fail` 对应最终等级 0；`unknown` 保留不确定性并优先进入专家复核。

## 5. 项目级特征设计

每个项目建议生成一组 0～1 的可审计特征。所有特征都应同时保存数值、计算依据、缺失原因和证据引用。

| 特征 | 科学含义 | 建议计算方式 |
|---|---|---|
| `semantic_relevance` | 项目研究主题与用户任务的相关性 | 英文 query terms、BM25/关键词证据、多语种 embedding、结构化语义分类共同计算；不能只依赖字符串命中 |
| `constraint_fit` | 物种、采集方式、标记、PTM、HLA 等条件是否满足 | 满足、未知、冲突分别编码；硬冲突进入 Hard gate |
| `requested_subset_coverage` | 混合项目中真正符合需求的数据子集大小 | 符合要求且可用的文件数、比例和分组覆盖；数量采用封顶或对数缩放，避免大项目无条件占优 |
| `bundle_completeness` | 任务所需文件角色是否成套 | 已满足的必要角色数 ÷ 任务要求角色数，例如 RAW、search result、metadata/SDRF |
| `task_readiness` | 数据能否直接进入特定建模任务 | 格式支持、标签来源、转换流程、exporter 和缺失需求综合计算 |
| `metadata_completeness` | 关键元数据是否充分 | 按任务相关字段加权统计物种、样本、仪器、碎裂、LC、PTM、标记、SDRF 等字段的已知比例 |
| `instrument_workflow_fit` | 仪器和实验流程是否适合用户任务 | 精确匹配、兼容、未知、冲突分级；不要把“仪器字段存在”误当成“仪器适合” |
| `evidence_confidence` | 判断所依据证据的可靠性 | 文件级/SDRF 证据优于项目描述；来源冲突、仅项目级推断和字段缺失降低可信度 |
| `accessibility_cost` | 获取和处理数据的实际可行性 | 下载地址、文件大小、格式、转换器、预计存储和计算成本 |

### 文件数量处理原则

文件总数不能直接线性加分。应优先使用：

- 符合需求的文件数量。
- 符合需求的文件比例。
- 是否覆盖必要文件角色。
- 文件数量的 `log1p` 或封顶变换。
- 混合数据类型项目中的目标子集是否可独立提取。

例如，一个包含 2,000 个无关文件的项目不应自动高于一个包含 30 个完整、可训练文件的项目。

## 6. 初版透明基线

在专家标签不足时，可先使用透明的人工基线：

```text
base_utility =
  0.30 × semantic_relevance
+ 0.20 × constraint_fit
+ 0.20 × requested_subset_coverage
+ 0.10 × bundle_completeness
+ 0.08 × task_readiness
+ 0.05 × metadata_completeness
+ 0.04 × evidence_confidence
+ 0.03 × accessibility_cost
```

初版等级映射仅作为待校准起点：

```text
base_utility >= 0.80 → 3
0.60～0.79            → 2
0.35～0.59            → 1
< 0.35                → 0
Hard gate fail        → 0
```

这些权重应明确标为 `expert_seeded_baseline/v1`，不能宣称已经通过实验验证。

## 7. 专家反馈学习

每个完成异构专家共识的项目形成一条训练数据：

```text
X = 项目特征、缺失模式、任务类型、Prompt 上下文
y = 专家共识等级 0/1/2/3
```

训练标签纳入规则：

- 两个独立专家正式一致，或第三专家形成可靠多数。
- 专家身份和候选生成模型独立性可验证。
- 置信度为中或高。
- 证据引用和缺失信息完整。
- `needs_adjudication` 不作为确定标签，或只作为低权重/未标注样本。
- 未来人类标签的训练权重高于模型专家标签。

不采用逐条即时在线更新。建议每积累约 100～300 个新标签后：

1. 生成版本化训练快照。
2. 按 Prompt/主题/时间/项目分组切分，避免同项目泄漏。
3. 训练序数逻辑回归或可解释树模型。
4. 比较等级准确率、quadratic weighted kappa、校准误差、NDCG、grade>=2 recall 和 Hard gate 违规率。
5. 影子运行新模型。
6. 只有整体提升且关键子群不退化时才发布。
7. 保留旧模型和回滚路径。

当跨任务、多领域标签达到数千级时，可尝试 LightGBM ranking；达到更大且稳定的数据规模后再评估神经网络。

### 多模型专家 Agent 设计

当前阶段的专家评审池由不同底层模型的 Agent 组成，而不是模拟不存在的人类专家。每个专家 Agent 都必须具有可审计的模型身份：

- provider。
- requested model id。
- API 实际返回的 resolved model id。
- model family。
- endpoint identity。
- identity verification 状态。

专家选择规则：

1. 两位首评专家必须来自不同模型家族，并尽量来自不同 provider。
2. 产生候选或参与 Discovery 推理的模型家族不能评审自己的候选。
3. 第三位专家应来自不同于两位首评专家的模型家族，且不能与候选生成模型冲突。
4. 同一底层模型即使使用不同 system prompt、温度、角色名或 endpoint alias，也只能算同一专家来源。
5. 无法验证 resolved model 或模型家族时，可以保留投票，但只能形成 `model_expert_provisional`，不能宣称正式共识。
6. 每位专家独立读取同一份盲化 Evidence Package；首评阶段不能看到其他专家的分数、解释或身份。
7. 专家 Agent 输出必须包含 Hard gate、0～3 等级、置信度、证据引用、缺失信息、证据冲突和面向用户的理由摘要。
8. Hard gate 冲突、等级差超过 1、低置信度、证据冲突或证据不足时触发第三票。

模型专家结果必须存入：

```text
model_expert_judgments
model_expert_consensus
```

不得写入：

```text
human_grades
human_verified
```

用于训练 Discovery 权重时，只纳入经过身份验证的跨模型正式共识。`model_expert_provisional`、低置信度结果和 `needs_adjudication` 默认不作为确定训练标签，避免把单一模型偏见循环写回评分系统。

推荐的专家 Panel 不是固定绑定某三个品牌模型，而是通过版本化 Profile registry 动态选择：

```text
候选生成模型 family: G
→ 首评专家 A: family != G
→ 首评专家 B: family != G 且 family != A
→ 第三专家 C: family != G/A/B（如果存在）
```

这样模型升级或供应商变化时可以更新 Profile，而不用重写共识逻辑。

### 主动学习

专家预算应优先分配给：

- 预测概率接近等级边界的项目。
- Hard gate 为 `unknown` 的项目。
- Discovery 模型与专家历史经常不一致的项目类型。
- 多专家分歧或低置信度项目。
- 对项目集覆盖具有较高边际价值的项目。

这比对所有项目平均投入三票更有效率。

## 8. Discovery 与专家统一 0～3 展示

用户界面统一成 0～3 是合理的，但不能覆盖来源：

```text
Discovery 预测：2 分，置信度 0.68
专家共识：3 分，置信度高
```

内部建议保存：

```json
{
  "predicted_grade": 2,
  "grade_probabilities": {"0": 0.04, "1": 0.18, "2": 0.52, "3": 0.26},
  "prediction_confidence": 0.68,
  "prediction_source": "learned_discovery/v1",
  "expert_consensus_grade": 3,
  "expert_consensus_status": "model_expert_consensus"
}
```

旧 `project_score/file_score` 可以在迁移期保留为诊断特征，但不再作为用户唯一看到的“最终评分”。

## 9. 混合数据类型项目的解释

项目评分必须基于用户需要的目标子集，而不是对整个项目做模糊平均。建议输出结构化依据并生成描述：

```text
该项目共包含 243 个文件，其中 37 个符合 DDA 免疫肽条件；其余文件主要属于 DIA 或普通蛋白质组实验。符合条件的子集包含 RAW 文件，但未发现完整配对的搜索结果，因此预测为 2 分，置信度中等。建议仅保留这 37 个目标文件，并进一步核对 SDRF 和 HLA 元数据。
```

项目解释至少包含：

- 项目总文件数和目标子集文件数。
- 目标子集主要类型。
- 不符合要求的主要类型。
- 已满足条件。
- 缺失、未知或冲突条件。
- 评分原因和置信度。
- 推荐保留的文件子集或下一步调查动作。

输出应是可审计的理由摘要，而不是暴露模型内部原始思维链。

## 10. 项目集选择与集合总分

单项目评分表示“这个项目自身有多适合”；集合选择还要考虑覆盖、多样性、冗余和成本。建议定义：

```text
SetScore =
  0.50 × 项目平均预期可用度
+ 0.20 × 目标项目数量完成度
+ 0.15 × 任务/实验类型覆盖度
+ 0.10 × 证据完整覆盖度
+ 0.05 × 多样性
- 冗余惩罚
- 成本与风险惩罚
```

其中单项目预期可用度可以取：

```text
E[grade] / 3
```

项目选择本质上应优化：

```text
项目质量 + 覆盖边际收益 + 多样性收益 - 冗余 - 成本
```

而不是简单按单项目分数排序后截断。

## 11. GrillMe Q7b 目标规模草案

Q7b 的主问题应以“最终可用项目数”为主，文件数作为并列或次级问题：

| 覆盖程度 | 推荐目标入选项目数 | 推荐候选池量级 | 说明 |
|---|---:|---:|---|
| 精选 | 约 10～30 | 约 50～100 | 先验证方向 |
| 均衡 | 约 50～100 | 约 200～300 | 与系统常见量级接近，但作为明确目标而非暗中截断 |
| 尽量搜全 | 约 150～300+，或安全上限内尽量多 | 候选池随之上调 | 停靠条件为覆盖目标、安全上限、边际收益不足或用户中止 |

评审调用量需要显式显示：100 个项目至少产生约 200 个首评模型调用，争议项目才产生第三票。大规模模式应采用启发式初筛、主动学习和分层专家审计，而不是所有项目无差别三票。

## 12. 语言本地化

整个 Build 应携带：

```text
output_language = zh-CN / en
```

规则：

- 搜索 `query_terms` 始终生成仓库友好的英文短语。
- 界面选择中文时，Prompt 解析说明、进度日志、警告、项目描述、缺失信息和专家总结输出中文。
- 界面选择英文时，所有用户可见说明输出英文。
- 内部稳定枚举和 reason code 保持英文，例如 `missing_search_results`。
- UI 将内部 code 本地化为“缺少搜索结果文件”。
- 不输出原始 chain-of-thought，只输出结构化、可审计的理由摘要。

当前专家 system prompt 固定为英文，且一键 build 尚未把 UI 语言传入 Prompt preparation、Discovery 和专家 job，这是后续需要修复的跨层契约。

## 13. 推荐实施阶段

1. 统一 0～3 等级语义和评分来源字段。
2. 将现有项目/文件启发式分拆为可审计特征，不再展示为最终科学分。
3. 实现目标文件子集识别和本地化项目解释。
4. 加入 `output_language` 全链路传播，英文搜索、选定语言解释。
5. 建立专家标签训练集和版本化快照。
6. 完善异构模型专家 Profile registry、resolved model 验证、生成模型冲突检查和第三专家选择。
7. 上线序数回归基线，先影子运行，不替换现有筛选。
8. 用主动学习挑选不确定项目进入专家评审。
9. 实现项目集优化和 Q7b 三档规模策略。

## 14. 周报可直接引用摘要

本周完成了 Benchmark Review 评分体系的下一阶段设计。现有 Discovery 的 `project_score`、`file_score`、AI-ready 和 Value 分属于规则驱动的启发式指标，适合快速初筛，但尚不能作为科学校准后的最终可用性评分。新方案将 Hard gate、项目特征、Discovery 预测、异构专家共识和项目集优化分层处理，并统一向用户展示 0～3 序数等级。当前没有真实人类专家，首期由不同底层模型家族的 Agent 组成专家 Panel：两位跨模型首评，争议时引入第三模型；候选生成模型不得评审自己的结果，无法验证模型独立性时只能形成 provisional 结论。经过验证的跨模型专家共识将作为高质量伪标签，定期离线训练序数模型或排序模型，以主动学习优先复核边界和低置信度项目，逐步更新 Discovery 权重。项目评分将重点计算语义相关度、约束匹配度、目标文件子集覆盖、文件包完整度、任务就绪度、元数据、仪器流程适配、证据可信度及获取成本；文件数量采用比例、封顶或对数处理，避免大项目凭数量获得虚高分。同时设计了项目集层面的覆盖、多样性、冗余和成本目标，以及精选、均衡、尽量搜全三档规模。语言方面，搜索词继续自动生成英文，而 Prompt 解析、进度、项目解释和专家总结将跟随用户选择的中文或英文输出。
