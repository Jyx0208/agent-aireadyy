# Carbon 产业级任务运行平台重构

## Goal

在不改变现有 PRIDE 检索、项目审查、文件筛选和 500 文件增量交付语义的前提下，把当前工作台升级为可长期运行、可恢复、可观察、可管理的产业级产品。用户应当能够快速打开系统，一眼判断当前任务在做什么、完成到哪里、为什么等待或失败，并能高效管理大量历史任务。

## Background

### Confirmed product problems

- 长任务、大任务文件和历史记录会显著拖慢 API 与页面；当前真实运行曾产生约 38 MB 的单任务 JSON。
- 当前过程展示偏向原始日志，任务阶段、关键词进度、审查批次、项目证据与文件交付之间缺少清晰层级。
- 当前任务状态不是稳定的实时权威状态；外层 `running` 与执行投影 `failed` 可以同时出现。
- 历史任务存在无效、重复和不完整记录，列表打开慢，缺少高效筛选、归档和空间治理。
- 前端存在固定视口高度和多个嵌套滚动区，鼠标滚轮容易失效或被错误容器截获，当前任务信息也会被挤压。

### Confirmed implementation facts

- 前端已经使用 `@carbon/react` 1.112.0、`@carbon/icons-react` 11.84.0 和 Carbon AI Chat；版本与 Carbon 官方文档当前 React 版本一致。问题不是缺少组件库，而是缺少统一的 Carbon 信息架构和 pattern 约束。
- `frontend/benchmark-review/src/App.tsx:169-220` 使用顶部 Tabs 承载所有产品区域，发现页由聊天、侧轨和运行进度自定义拼装。
- `frontend/benchmark-review/src/styles.css:20-73` 使用 `overflow: hidden`、固定 `100dvh` 派生高度以及多个 `overflow-y: auto` 容器；`styles.css:825-838` 在窄屏直接隐藏运行进度工作区。
- `frontend/benchmark-review/src/CarbonAgentChat.tsx:412-420` 对运行中发现任务每秒请求一次摘要；`App.tsx:91-116` 对从历史恢复的任务每两秒轮询一次。
- `src/agent/web/app.py:16547-16610` 将任务状态、执行投影、日志、结果批次和结果记录组合成同一个发现任务响应。
- `src/agent/web/app.py:16700-16722` 将最多 2,000 条日志与完整任务记录继续放在同一个持久化 JSON 中。
- `src/agent/web/app.py:16725-16778` 每次持久化都原子重写完整任务 JSON、摘要 sidecar 和日志文件。
- `src/agent/web/app.py:17374-17461` 在每个发现事件或仓库搜索事件上更新内存状态并持久化整个任务。
- `src/agent/web/app.py:17213-17371` 已有执行状态 reducer，可作为权威状态机的迁移基础，不应在 React 中重新推断状态。
- `src/agent/web/app.py:19097-19141` 已有普通任务 WebSocket，但发现任务没有等价的增量状态通道。
- `src/agent/web/app.py:15301-15362` 已有轻量历史摘要路径，但 API 仍返回未分页集合；`frontend/benchmark-review/src/HistoryPanel.tsx:145-165` 直接渲染整个集合。
- `.trellis/tasks/07-28-history-batch-storage-lifecycle/` 已设计历史复用、精确 500 文件批次、安全删除和源文件清理；本任务必须复用并深化该设计，不能另建冲突机制。

### Confirmed deployment boundary

- 第一阶段以当前 Windows 单服务器为生产基线，优先解决任务耐久性、实时状态、性能、历史治理和可用性。
- 本任务不以多节点、多服务器或分布式部署为目标；产业化重点是单服务器上的事务数据库、快速索引、稳定后台任务和高效查询。
- 状态存储、事件、项目、文件、历史摘要和磁盘资产需要清晰的数据模型，不能继续依赖前端轮询并解析大型 JSON 文件。
- 不引入分布式锁、复杂 RBAC、多数据中心运维或仅为未来集群准备的基础设施。

### Confirmed primary interaction model

- 策略确认前以 Agent 对话为主要工作区，用于表达目标、补齐约束、选择关键词和确认执行策略。
- 任务启动后默认切换到“当前任务控制台”，以结构化进度、Worker、项目证据、文件批次和异常恢复为主要内容。
- 对话不会消失；运行中作为“任务对话”辅助页签保留，用户可以随时补充指令或询问状态。
- 刷新页面或从历史重新打开运行任务时，默认恢复控制台而不是回到空白对话。

### Confirmed implementation principle

- 优先采用成熟、维护活跃、许可兼容并且支持 Windows 单服务器的现成方案，不从头重写数据库 ORM、迁移系统、任务队列、SSE 协议、查询缓存、表格交互或设计系统。
- 复用项目已经存在的 SQLite WAL、Agent control-plane event store、repository index、Pydantic 模型、FastAPI 和 Carbon 组件。
- 自研代码集中在 PRIDE 检索、蛋白质组学项目/文件审查、业务状态投影和现成组件之间的薄适配层。
- 每个新增基础设施依赖必须在设计文档中说明维护状态、Windows 支持、许可证、替代方案、引入成本和退出路径。

### Confirmed release model

- 本次改造采用一次性完整替换，不向用户交付数据库完成但前端未完成、或新前端完成但实时状态仍依赖旧 JSON 的中间产品。
- 开发和验证期间现有已部署服务保持可用；新架构在隔离工作区完成全部后端、数据迁移、实时通道和 Carbon 前端。
- 只有完整回归、恢复、性能、可访问性和迁移演练全部通过后，才进行一次统一切换。
- 内部仍按依赖顺序实施并设置回滚点；内部顺序不构成对外分批交付。

## Requirements

### R1 — Carbon-first design governance

- 每个主要页面和交互必须先映射到 Carbon 官方 component、pattern 或 template，再决定是否编写自定义实现。
- 建立并维护“用户目标 → Carbon pattern → Carbon component → 项目实现”的设计映射表，作为设计评审和代码评审依据。
- 默认使用 Carbon Grid、spacing、type、color、layer 和 motion token；不得用任意像素、任意颜色和私有交互重新实现已有 Carbon 语义。
- 自定义组件只允许用于蛋白质组学领域内容或 Carbon 明确缺失的能力，并在设计文档中记录缺口、可访问性责任和退回 Carbon 的条件。
- 必须通过键盘导航、焦点顺序、屏幕阅读器标签、缩放和 reduced-motion 检查。

### R2 — 清晰稳定的产品信息架构

- 使用 Carbon UI Shell 建立持久导航，将“当前任务”“历史任务”“批量处理”“单文件处理”“系统设置”作为稳定产品区域，而不是挤在一个可横向溢出的 TabList 中。
- “当前任务”是一级主工作区，完整展示任务目标、权威状态、最近心跳、阶段进度、当前关键词、审查队列、文件交付和停止/恢复动作。
- 当前任务页采用明确的双模式：任务开始前呈现策略对话；任务开始后默认呈现运行控制台，并提供“任务对话”入口。
- 从对话切换到控制台不得丢失对话、确认策略、当前选择或任务引用；控制台也不得从聊天消息反向推导权威进度。
- 主进度不得放在 Carbon right panel；right panel 只用于选中项目的证据详情或系统级辅助信息，符合官方 right panel 用途。
- 页面只保留一个主要纵向滚动上下文；局部滚动必须有明确边界、标题、键盘可达性和滚动接力行为。
- 在 1280×720、1440×900、1920×1080 和常见窄屏宽度下，当前状态与主要动作都不得被隐藏。

### R3 — 单一权威任务状态机

- 后端必须拥有唯一状态机，至少覆盖 `queued`、`searching`、`reviewing`、`finalizing`、`completed`、`blocked`、`failed`、`cancelled`、`interrupted`。
- 顶层任务状态、执行阶段和前端状态必须来自同一投影，不允许出现无法解释的 `running + failed` 组合。
- 权威快照必须包含单调递增版本/事件序号、最后更新时间、Worker 心跳、当前关键词、关键词总数、候选数、已审数、待审数、当前批次和可恢复性。
- 每次状态转移必须记录原因、触发事件和前一状态；非法转移应被拒绝并产生结构化诊断事件。

### R4 — 增量实时状态与断线恢复

- 发现任务提供独立的实时事件通道；首选 Server-Sent Events，因为主要数据流是服务器单向推送到浏览器。
- 客户端使用事件序号和 `Last-Event-ID` 续传；断线后先获取小型权威快照，再补齐缺失事件。
- REST 快照作为首次加载、刷新和实时通道失败时的兜底，不再以高频全量轮询作为主要机制。
- 前端必须明确区分“任务没有推进”“连接中断”“Worker 无心跳”“正在等待外部 API/模型”和“任务失败”。
- 停止、恢复和重新连接不会丢失已完成的关键词、项目审查、证据或已发布批次。

### R5 — 状态、事件、证据与大文件分离

- 权威任务快照必须保持小且可快速读取；运行日志不能嵌入快照。
- 任务事件采用追加写入和分页读取；项目审查与文件记录采用独立、可索引的数据实体。
- 大型原始响应、模型轨迹、审计材料和导出文件放在受管理文件存储中，只在数据库保存索引、摘要和校验信息。
- 单个普通状态事件不得触发完整任务 JSON、完整日志文件或完整历史索引的重写。
- 迁移过程中保留旧任务只读兼容和恢复能力，并提供可回滚的双读/回退路径。

### R6 — 大规模性能指标

- 运行状态快照响应体目标不超过 100 KB；正常增量事件目标不超过 16 KB。
- 在目标部署环境中，1,000 个历史任务下历史首页首屏 API p95 不超过 1 秒，前端可交互时间不超过 2 秒。
- 765 个候选项目、20,000 个文件线索和 10,000 个事件的任务不得把全部数据一次发送或一次渲染到浏览器。
- 服务端负责历史、项目、文件和事件的分页、筛选与排序；前端仅保留当前可见窗口和必要缓存。
- 后台任务运行时，健康检查和轻量状态 API 不得等待大型任务文件锁或目录扫描。
- 长列表操作不得产生超过 100 ms 的主线程阻塞；滚动过程中不应出现持续掉帧或滚轮失效。

### R7 — 可理解的运行过程

- Carbon ProgressIndicator 表达稳定业务阶段，ProgressBar 表达可计算数量；未知进度才使用 indeterminate。
- 运行过程按“关键词检索 → 内部分页 → 全局去重 → 审查批次 → 项目证据 → 文件判断 → 批次发布”分层展示。
- 每个项目必须能看到当前步骤、metadata/SDRF/文件检查结果、使用的证据、入选或排除理由、分数/置信度以及耗时。
- 并行审查必须显示 Worker 槽位与各自正在处理的项目，不能把同一阶段误画成无限并行。
- 错误必须展示作用范围、失败原因、重试次数、下一动作和是否影响整体完成；原始技术日志按需展开。

### R8 — 可扩展的历史与磁盘治理

- 历史页使用 Carbon DataTable、服务端分页、排序、搜索、batch filtering 和批量操作。
- 默认视图区分运行中、需处理、已完成、已归档和回收站；空壳、损坏和开发测试记录不得污染默认业务列表。
- 支持按任务类型、状态、时间、检索主题、物种、项目数、文件数和磁盘占用筛选。
- 历史任务摘要不得读取完整运行日志；打开详情时按需加载项目、文件、批次和事件。
- 复用 `.trellis/tasks/07-28-history-batch-storage-lifecycle/` 的安全删除、空间预览、可恢复删除、关联批次和源文件清理规则。

### R9 — Carbon 状态反馈

- 使用 Skeleton 表达首次结构加载，InlineLoading 表达局部短时操作。
- 使用 InlineNotification 呈现当前上下文中的可操作错误，Toast 或通知中心呈现后台任务状态变化。
- 避免多个 spinner、重复通知和无法定位来源的全局错误。
- 所有后台状态变化必须包含任务标识、时间和跳转目标。

### R10 — 科学与运行语义不回退

- 不改变已经确认的关键词顺序、逐词拉取到末尾、全局去重、并行审查、开放候选池和 500 文件增量交付语义。
- 不因前端重构删除已持久化任务、对话、审查证据、已发布批次或文件清单。
- 现有运行中的发现任务不参与结构迁移写入；迁移只能在明确的安全边界之后进行。

### R11 — 单服务器事务数据库与快速索引

- 本次交付必须能作为 Windows 服务长期运行，Web 服务、后台 Worker 和持久化存储有独立生命周期；Web 服务重启不得把运行任务直接判为丢失。
- 使用适合 Windows 单服务器的事务型数据库保存任务快照、事件索引、关键词、项目、文件、批次、资产和删除请求。
- 针对状态、更新时间、任务类型、关键词、项目编号、审查状态、文件可交付状态和事件序号建立明确索引。
- 历史、项目、文件和事件列表必须使用数据库分页查询，不得在请求时扫描任务目录或加载完整 JSON。
- Worker 不得以 Web 进程内内存字典作为唯一运行权威；任务认领、心跳、取消和恢复必须可持久化。

### R12 — 成熟方案优先与自研边界

- 数据访问和 schema migration 使用成熟库管理事务、连接、索引和版本升级，不在 `app.py` 中继续堆叠手写建表与迁移分支。
- 后台任务认领、重试、定时协调和失败记录优先采用支持 Windows 与本地持久化的成熟任务队列，不自行实现不完整的调度器。
- SSE 使用成熟的 ASGI/FastAPI 实现，覆盖 keepalive、断线、代理缓冲和 `Last-Event-ID`，不只拼接字符串模拟协议。
- 前端服务器状态、缓存、取消、重试和失效刷新使用成熟查询库；Carbon 继续负责视觉与交互语义。
- 技术设计必须包含“直接采用 / 扩展复用 / 必须自研”矩阵；任何基础设施自研项都需要证明现有方案不满足要求。

### R13 — 单次完整切换

- 新数据库、历史索引、Huey Worker、SSE API、Carbon UI Shell、当前任务控制台和历史管理必须作为一个完整发布单元验收。
- 切换前必须完成真实旧数据的只读迁移演练，并保留原 JSON、manifest 和任务目录备份。
- 新版本不得向用户暴露旧页面和新页面并存的长期双轨产品；兼容适配器仅用于迁移和回滚。
- 切换必须有明确维护窗口、预检查、数据库备份、构建物校验、健康检查、冒烟测试和一键回滚步骤。

## Acceptance Criteria

- [ ] AC1：设计文档包含完整的 Carbon 映射表；每个主要界面元素都有官方 component/pattern 来源或记录充分的例外。
- [ ] AC2：当前任务页在支持的视口中无需进入右侧窄栏即可看到状态、心跳、阶段、数量进度、当前工作和主要动作。
- [ ] AC2a：确认前默认进入策略对话；任务开始、刷新或从历史恢复运行任务后默认进入对应控制台，并可无损切回任务对话。
- [ ] AC3：整页只有一个主要纵向滚动上下文；鼠标、触控板和键盘滚动测试均不会被嵌套容器截获。
- [ ] AC4：权威状态机测试覆盖所有合法和非法转移，且 API 不会返回语义冲突的顶层状态与执行阶段。
- [ ] AC5：实时事件在服务器提交后 1 秒内反映到同一局域网浏览器；断线重连不重复或遗漏事件。
- [ ] AC6：运行状态接口不读取或返回完整任务日志与项目结果，响应体满足 100 KB 目标。
- [ ] AC7：每个项目的 metadata、SDRF、文件检查、判断理由、证据和结果可以按需查看；并行 Worker 状态可辨认。
- [ ] AC8：1,000 个历史任务的首页、筛选和翻页满足性能目标，不扫描所有任务目录或加载全部详情。
- [ ] AC9：历史默认列表隐藏无效/开发记录，并支持归档、回收站、安全删除预览和磁盘空间统计。
- [ ] AC10：使用包含 765 个候选、20,000 个文件和 10,000 个事件的基准夹具完成 API、浏览器和内存性能验证。
- [ ] AC11：既有检索、审查、恢复、停止、500 文件批次和历史复用回归测试通过。
- [ ] AC12：Carbon 可访问性、键盘导航、焦点管理、缩放和 reduced-motion 检查通过。
- [ ] AC13：Web 服务重启后可从本地事务数据库恢复任务监控；历史首页、项目筛选、事件续传和文件分页均命中可验证的数据库索引。
- [ ] AC14：技术设计中的成熟方案矩阵通过评审；数据库迁移、任务队列、SSE、查询缓存和 Carbon 交互没有无依据的重复造轮子。
- [ ] AC15：所有功能在同一候选发布版本中通过验收后才切换；切换失败可恢复旧服务、原任务 JSON 和原历史索引。

## Out of Scope

- 改写免疫肽项目科学评分、项目/文件纳入规则或 PRIDE 搜索语义。
- 引入 Payload CMS 或第二套全栈管理后台。
- 本次实现跨数据中心、多租户计费或复杂 RBAC。
- 多节点、多服务器、分布式数据库和高可用集群。
- 无确认地自动删除用户源文件或运行中任务。
