# Discovery Agent v3 Benchmark 与实验计划

## 1. 这套实验要回答什么

这套 benchmark 不是为了尽快得到一个“Agent 胜过 Workflow”的数字，而是为了回答三个可以检查的问题：

1. 不优先考虑 Token 和耗时，哪套系统能给出更准确、更完整的 AI-ready 数据清单？
2. Agent 的搜索规划、失败恢复和证据补全是否带来了真实提升，而不只是使用了更多请求？
3. Agent 还会在哪些任务、表达方式和故障条件下失败？

当前阶段是内部优化与筛错。使用同系列模型自动判卷得到的结果只能称为“内部临时评价”。加入不同系列模型或人工复核后，才能称为“独立验证”。

Workflow 暂时保留为对照，不列入删除计划。最终目标仍然是把 Agent 优化到在结果质量上稳定超过 Workflow。

## 2. 为什么不再从已知 PXD 项目倒推问题

旧版诊断集先选择少量已知项目，再根据这些项目编写问题。它适合检查系统能否找回已知答案，但容易让问题贴合答案，不能充分代表真实用户需求。

v3 改为任务优先：先写真实的 AI-ready 数据需求，不预设必须找到哪个 PXD 项目，再让 Agent 和 Workflow 独立搜索。只有两套系统完成搜索后，才构建候选池并评价项目。

## 3. 题库设计

题库覆盖六类任务：

1. 肽段保留时间预测
2. 碎片强度预测
3. PSM 打分
4. PTM / de novo
5. 嵌合谱解析
6. 普通 de novo 测序

每类任务包含三种用户表达：

- **明确**：目标、物种、采集方式、文件和多样性要求较完整。
- **普通**：研究目标清楚，但只给出主要条件。
- **模糊**：主要描述想解决的问题，需要系统识别缺失信息。

共建立两套题：

- **开发集 18 题**：用于反复诊断和优化。
- **冻结保留集 18 题**：研究场景和实验条件不同，只在阶段性版本上运行。

保留集在首次正式运行前冻结文件内容、版本和 SHA-256 校验值。运行后不得根据结果修改题目或评分规则。

### 3.1 模糊需求的行为原则

模糊需求采用“能行动就先行动，关键歧义才澄清”：

- 可以安全推断的内容先做可逆搜索。
- 用户没有说出的条件不能偷偷变成硬约束。
- 对多个合理方向先探索并比较。
- 只有歧义会根本改变数据选择时才请求澄清。
- 测试可提供模拟用户回答，检查系统得到澄清后是否正确调整。

## 4. 两条对比赛道

### 4.1 质量优先赛道（主结论）

Workflow 使用当前调优后的固定流程。Agent 在服务器安全硬上限内自主决定查询数量、搜索轮数、项目检查深度和停止时机。主要比较最终答案质量，不要求两边消耗相同资源。

### 4.2 同预算赛道（解释性实验）

两边使用相近的仓库请求上限，观察 Agent 是否能用相同资源得到更好的结果。这条赛道用于解释提升来自规划能力还是更多搜索，不决定产品最终选择。

Token、耗时、模型回合和仓库请求全部记录，但只在无限循环、超时、上下文丢失或超过安全硬上限时构成失败。

## 5. 高召回候选池

只评价两套系统最终选择的项目会漏掉“两边都没有找到的好项目”。因此每道题构建三个来源的候选池：

1. Workflow 搜索和检查过的项目。
2. Agent 搜索和检查过的项目。
3. 不参赛的中立高召回构建器找到的项目。

中立构建器使用预先定义的任务词、物种词、采集方式和同义词进行宽泛、原子化搜索。它不读取 Agent 推理，不根据胜负改变策略，也不生成最终答案。

三个来源合并、去重并缓存当次 PRIDE 元数据。盲评文件隐藏项目来源、系统名称和项目编号。该候选池是“当前可见的高召回候选池”，不是 PRIDE 全库的绝对真值。

## 6. 自动盲评和人工复核

### 6.1 评分流程

每个候选项目先进行两次独立自动盲评：

- 两次一致：使用该分数。
- 两次不一致：再追加三次，总共五次。
- 五次评分使用中位数定分。

每次评价保存模型、提示词版本、评分、简短证据理由和时间。判卷不接收 Agent 或 Workflow 的推荐理由，只接收原始任务和仓库事实。

### 6.2 置信度

- **高置信度**：至少四次给出相同分数。
- **中置信度**：多数评分一致，且评分基本只相差一级。
- **低置信度**：评分跨度较大，例如同时出现 0 分和 3 分。

低置信度样本仍参与内部分析，但报告必须同时给出“包含全部样本”和“排除低置信度样本”的结果。两个结果方向不一致时不能宣布稳定领先。

### 6.3 评分来源

评分来源必须明确标记：

- `seed`：旧题库预置诊断分数。
- `provisional_same_family`：与执行 Agent 同系列模型的临时评分。
- `provisional_independent_model`：不同模型系列、尚未人工确认的评分。
- `human_verified`：人工复核评分。

同系列模型评分不能通过正式替代门槛。当前先复用已保存的 DeepSeek API 配置；数据结构预留多模型评价，未来接入第二模型时不重做历史 benchmark。

### 6.4 评价页面

`/benchmark-review` 保留人工逐条评分能力，同时增加自动评价结果：

- 展示临时分数、全部模型投票、置信度和证据理由。
- 优先显示低置信度、硬约束冲突和可能改变胜负的样本。
- 人工评分作为新记录保存，不覆盖自动评价历史。
- 支持查看自动与人工一致率和分歧样本。
- 支持导出 JSON 和中文 Markdown 实验记录。

## 7. 分层评价，不让错误被平均分掩盖

评价按照以下顺序进行：

1. **硬约束门槛**：明确物种、采集方式、标签方式等不能违反。
2. **文件级任务就绪门槛**：目标任务必需的数据类型必须配套。
3. **项目相关性与排序质量**：评价优质项目是否排在前面。
4. **搜索覆盖率**：评价高分候选的找回情况和共同遗漏。
5. **证据完整性**：评价结论是否由可追溯仓库事实支持。
6. **稳定性与恢复能力**：单独作为发行门槛。
7. **资源消耗**：用于解释，不抵消质量，也不掩盖错误。

可以生成绘图用的综合质量分，但报告必须同时展示各组成项和门槛状态。

## 8. 项目级和文件级评价

项目发现和最终数据清单分别评分：

- 项目是否符合生物学任务和明确约束。
- 最终选择的原始谱图、鉴定结果、实验设计和元数据是否配套。
- 是否混入明显无关文件。
- 原始文件与结果文件是否能够建立关系。
- 数据是否达到对应 AI 任务的最低可训练条件。

找到好项目但选错文件不能得到完整的 AI-ready 分数。

## 9. 重复运行策略

- 日常修复：受影响题目先运行 1 次。
- 开发集阶段检查：18 题每题运行 2 次。
- 冻结保留集：18 题每题运行 3 次，报告中位表现和最差一次。
- 接近替代门槛的版本：质量优先赛道必须完成 3 次重复；同预算赛道可先运行 2 次。

报告同时检查平均表现、最差表现、结果波动和模糊需求下的选择稳定性。

## 10. 替代门槛

现在固定不可协商的原则，开发集测得自然波动后校准一次数值，并在运行保留集前冻结。

固定原则：

- Agent 不增加硬约束错误。
- 六类任务中不能有某一类持续输给 Workflow。
- 明确、普通、模糊三组分别报告和达标。
- 包含全部样本和排除低置信度样本后，结论方向一致。
- Agent 最差运行不能出现严重退化。
- 保留集与开发集的结论方向一致。
- 同系列模型临时评分不能形成正式替代结论。

初始数值目标：

- Agent 胜率至少 65%。
- Workflow 胜率不超过 10%。
- 平均质量提升超过测得噪声的两倍。
- 模糊问题的提升应高于明确问题。
- 每个任务类别的中位质量差不得为负。

这些数字在开发集噪声校准后只允许冻结一次，保留集运行后不得移动门槛。

## 11. 故障恢复与韧性实验

故障测试不混入真实检索质量分，但必须通过发行门槛：

- 首次搜索返回零结果。
- 查询过严，需要原子化或语义放宽。
- 请求超时或返回 429。
- 项目元数据或文件证据缺失。
- 多个查询返回重复候选。
- 连续返回低质量结果。
- 预算接近硬上限。

检查 Agent 是否能观察异常、诊断原因、改变策略、保存有效状态并完成最终选择。

## 12. 实验记录必须保存的内容

每次实验至少保存：

- 代码提交、分支和题库版本。
- PRIDE 查询、响应缓存时间和候选项目。
- Agent 与 Workflow 的完整公开事件日志。
- 模型名称、API 基地址、提示词版本和预算硬上限；不保存明文 API key。
- 仓库请求数、模型回合、输入输出 Token 和耗时。
- 最终项目和文件清单。
- 每次自动评分、理由、置信度和评分来源。
- 人工覆盖记录及理由。
- 各门槛结果、失败分类和结论适用范围。

## 13. 实施顺序

1. 完成并版本化本设计文档。
2. 修正评分来源标记和正式结论门禁。
3. 建立 18 题开发集和 18 题冻结保留集。
4. 实现两次初判、分歧追加至五次的自动盲评。
5. 实现中立高召回候选池。
6. 完善项目级和文件级评价。
7. 建立故障恢复测试集。
8. 选两类任务共 6 题运行小型试验。
9. 扩展到开发集，测量噪声并冻结数值门槛。
10. 根据真实失败类型优化 Agent。
11. 锁定代码、题库、评分规则和门槛后运行冻结保留集。

## 14. 当前可以和不可以得出的结论

当前自动实验可以说明：

- 哪套系统更少违反客观约束。
- 哪套系统的项目和文件清单更适合目标任务。
- Agent 的恢复、证据补全和动态搜索是否真实发生。
- 自动评价是否稳定偏向某一套系统。

当前自动实验不能单独说明：

- 专业人员已经证明 Agent 全面超过 Workflow。
- 高召回候选池包含 PRIDE 的全部正确项目。
- 同一个判卷模型重复五次等价于五位独立专家。

这些边界必须保留在实验报告中，直到不同模型系列或人工复核提供独立证据。
