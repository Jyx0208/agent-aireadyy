# 这次 Benchmark 到底是怎么来的

## 一句话说明

这次 benchmark 的做法其实很简单：

1. 先选了 3 个我们已经知道答案的 PRIDE 项目。
2. 根据这 3 个项目，反过来设计 3 个搜索问题。
3. 再把每个问题改写成 4 种难度。
4. 让 Workflow 和 Agent 分别回答这 12 个问题。
5. 比较它们找到了什么、有没有找到已知项目、用了多少请求、花了多长时间。

所以它是我们自己做的开发测试，不是从论文或公开排行榜下载的 benchmark。

## 第一步：先选三个已知项目

为了测试 Discovery，首先需要知道“至少有一个正确答案”。

因此最开始选了下面三个 PRIDE 项目。

### 1. `PXD000900`

这是一个已知的 HeLa 多蛋白酶质谱项目。

我们用它测试系统能不能理解并组合这些条件：

- HeLa；
- 使用多种蛋白酶；
- DDA；
- label-free；
- Orbitrap；
- 适合做覆盖面较广的蛋白质组数据。

### 2. `PXD074954`

这个项目与人 iPSC 衍生感觉神经元、化疗造成的神经损伤和神经保护药物有关。

我们用它测试系统能不能理解一个比较长的生物学研究目标，而不是只会匹配一个简单关键词。

### 3. `PXD077080`

这是一个人细胞系 HLA 免疫肽组学项目。

我们用它测试系统能不能理解：

- HLA 和 MHC；
- 免疫肽组学；
- 免疫亲和富集；
- 人细胞系；
- 质谱采集数据。

这三个项目就是最初的“已知答案”。

但要注意：它们只是我们提前知道的正确项目，不代表每个问题只有这一个正确答案。

## 第二步：根据三个项目反向设计问题

知道项目以后，我们根据项目内容反向写了三个问题。

### 问题一：寻找 HeLa 多酶切数据

完整目标大致是：

> 找人源 HeLa 多蛋白酶、label-free DDA、Orbitrap 蛋白质组数据。

希望系统找到 `PXD000900`。

### 问题二：寻找 iPSC 感觉神经元神经保护数据

完整目标大致是：

> 找人 iPSC 衍生感觉神经元中，用于研究化疗神经损伤和神经保护药物的 DDA 蛋白质组数据。

希望系统找到 `PXD074954`。

### 问题三：寻找人细胞系免疫肽组学数据

完整目标大致是：

> 找从人细胞系中免疫纯化得到的 HLA 或 MHC 肽质谱数据。

希望系统找到 `PXD077080`。

所以这三个问题不是从真实用户问题库中抽出来的，而是根据已知项目人工写出来的。

## 第三步：每个问题改成四种难度

如果只使用完整问题，Workflow 和 Agent 都可能表现得不错，很难看出 Agent 的价值。

因此我们把每个问题改写成四个版本。

下面用免疫肽组学问题举例。

### 1. 条件完整

> 寻找人细胞系 HLA/MHC 免疫肽组学数据，要求免疫亲和富集、label-free DDA 和 Q Exactive 类仪器。

这个版本几乎把答案需要的关键词都说出来了。

### 2. 表达清晰

> 寻找从人细胞系免疫纯化得到的 HLA 肽质谱数据。

用户说清楚了研究对象，但没有把所有技术条件都列出来。

### 3. 表达模糊

> 我需要人细胞系数据，用来训练研究免疫系统展示肽段的模型。

用户说了研究目的，但没有直接说 HLA、MHC 或免疫亲和富集。

### 4. 存在歧义

> 寻找用于模型训练的人类肽呈递数据。

这个问题可能有很多合理解释。一个好的 Agent 应该意识到信息不够，必要时先问用户。

三个问题各有四个版本：

```text
3 个已知项目 × 4 种问题难度 = 12 道题
```

这 12 道题就是当前 benchmark。

## 第四步：Workflow 和 Agent 分别回答

每一道题都运行两次：

```text
Workflow 回答一次
Agent 回答一次
```

因此第一轮一共运行：

```text
12 道题 × 2 套系统 = 24 次 Discovery
```

两套系统都实时搜索 PRIDE。

我们记录：

- 它搜索了什么关键词；
- 检查了哪些项目；
- 最后选了哪些项目和文件；
- 有没有找到提前知道的项目；
- 有没有违反用户明确说出的物种等条件；
- 调用了多少次 PRIDE；
- 花了多长时间；
- Agent 为什么继续搜索或停止。

这里没有训练模型，只是在做两套搜索系统的对比实验。

## 第五步：之前是怎么打分的

最开始的评分非常粗糙。

我们只提前标记了几个项目：

```text
PXD000900 = 3 分
PXD074954 = 3 分
PXD077080 = 3 分
```

`3 分`表示它直接符合我们设计问题时心里想找的项目。

HeLa 问题还额外标了三个相关但不完全符合的项目：

```text
PXD073683 = 1 分
PXD077805 = 1 分
PXD064794 = 1 分
```

真正的问题是：其他没有提前标记的项目，程序暂时都按 `0 分`处理。

这并不合理。

例如 Agent 可能找到了一个非常好的新免疫肽组学项目，但只要它不是我们提前写下来的 `PXD077080`，程序就可能把它当成 0 分。

所以之前的自动评分只能用来快速发现问题，不能当成正式专家评价。

## 第一轮结果应该怎么理解

第一轮得到的暂定结果是：

```text
Agent 6 胜、3 平、3 负
```

这句话准确的意思是：

> 按照我们提前写下来的少量项目编号，Agent 暂时是 6 胜、3 平、3 负。

它不是说：

> 经过专家评价，Agent 在 12 个真实任务中有 6 次比 Workflow 更好。

因为大量新找到的项目还没有人工评价。

## 那之前的测试有什么用

之前的测试没有白做。它发现了几个真正的系统问题。

### 1. Agent 的候选曾被系统提前裁掉

Agent 检查过一些项目，但在最终选择前，旧的确定性规则已经先把候选池压缩了。

这意味着最后结果不完全是 Agent 自己决定的。

这个问题已经在当前工作区修改。

### 2. Agent 在免疫肽组学上不稳定

它有时能找到正确方向，有时会选择主题相关但不够合适的项目。

### 3. Agent 会知道自己还需要搜索，却提前结束

一次复测中，Agent 自己写着“还需要针对性第二轮搜索”，但它随后直接提交了结果。

原因是控制面只检查“有没有可用文件”，没有记录 Agent 一共检查过多少高相关候选。

现在已经改成：

- 记录累计检查过的项目编号；
- 候选较少时仍然可以快速结束；
- 高相关候选较多时，最低检查数量为“高相关候选数、最终项目上限的两倍、10”三者中的最小值；
- 没达到最低数量、预算又还有余量时，不允许提交最终结果；
- 工具会直接告诉 Agent“已经检查多少、最低需要多少、现在能不能提交”。

修复后重新运行了同一个免疫肽组学 clear 问题：

```text
修复前：检查 1 批后结束，没有选中 PXD077080，暂定质量差 -0.444
修复后：检查 2 批、累计 11 个候选，选中 PXD077080，暂定质量差 +0.119
```

修复后 Agent 使用 54 次 PRIDE 请求，Workflow 使用 61 次；Agent 用时 333.9 秒，Workflow 用时 226.0 秒。

这说明提前结束问题已经被修复并通过真实 PRIDE 复测，但 Agent 仍然明显更慢。

### 4. Agent 请求更少，但速度更慢

第一轮中，Agent 的 PRIDE 请求大约少 16.9%，但总耗时大约高 83.9%。

这说明 Agent 减少了仓库操作，却在模型回合和上下文处理上花了更多时间。

因此，之前测试的主要价值是发现架构问题，不是证明 Agent 已经胜出。

## 当前 Benchmark 的真实定位

当前 benchmark 更准确的名字应该是：

> Discovery Agent 内部人工开发测试集。

它适合：

- 开发过程中检查功能；
- 比较搜索行为；
- 定位 Agent 为什么失败；
- 做代码回归测试。

它还不适合：

- 宣称 Agent 已经超过 Workflow；
- 作为行业公开 benchmark；
- 作为专家认可的金标准；
- 用来给不同蛋白质组学 Agent 排名。

## 下一步怎么把它变得可信

下一步不能继续只看三个已知项目，而应该这样做。

### 1. 合并双方找到的所有项目

每道题运行完以后，把 Workflow 和 Agent 找到的项目放在一起去重。

第一轮已经整理出 70 个“问题版本 + 项目”候选。

### 2. 隐藏项目来源

评价人员不能知道一个项目来自 Workflow 还是 Agent，否则容易产生偏见。

### 3. 让蛋白质组学人员逐个评价

对每个项目判断：

- `3 分`：直接满足用户问题；
- `2 分`：高度相关，可以使用，但有小缺口；
- `1 分`：主题相关，但不是合适答案；
- `0 分`：无关或违反明确条件。

最好由两个人独立评价，有明显分歧时再找第三个人确认。

### 4. 模糊问题按用户实际说的话评价

不能因为我们心里想找 `PXD077080`，就把其他合理的“人类肽呈递数据”都判成错误。

如果问题本身信息不足，还要单独评价 Agent 是否应该先向用户提问。

### 5. 增加真实问题

正式 benchmark 应该加入：

- 真实研究人员提出的问题；
- 中文问题；
- 不同蛋白质组学任务；
- 不同下游 AI 任务；
- 不存在唯一正确项目的问题；
- 必须主动澄清的问题。

## 最后再用一句话说明

之前的流程是：

```text
先选三个已知 PRIDE 项目
→ 根据项目反向设计三个问题
→ 每个问题改写成四种难度
→ 得到十二道人工测试题
→ Workflow 和 Agent 各运行一次
→ 共运行二十四次 Discovery
→ 用少量已知项目编号做暂时评分
→ 主要用来发现 Agent 的系统问题
```

所以，之前测的是：

> Agent 和 Workflow 对我们人工设计的 12 道 PRIDE 搜索题分别表现怎样。

之前没有测的是：

> Agent 是否已经在一个公开、专家标注、具有代表性的蛋白质组学 benchmark 上全面超过 Workflow。
